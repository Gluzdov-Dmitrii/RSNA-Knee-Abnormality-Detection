# Протокол локальной валидации SPRINT943

`evaluate_oof.py` — независимый CPU evaluator без внешних зависимостей. Он считает
две **диагностические** метрики, проверяет целостность CSV и сохраняет provenance,
SHA256 входов, покрытие каждого target и показатели каждого fold. Обучение и
подбор весов ансамбля здесь не выполняются.

## Воспроизведение

Из корня проекта (PowerShell; `-S` отключает импорт site-packages, они не нужны):

```powershell
python -S experiments/SPRINT943/evaluate_oof.py `
  --predictions tmp/rebuilt_oof/r2p_full/oof.csv `
  --prediction-kind fold-out `
  --provenance "Existing S24 R(2+1)D18 predictions rebuilt 2026-09-14 from per-fold checkpoints on FOLDS_V1. No training performed in this sprint. Validation-epoch checkpoint selection on the same folds; see ops/reports/2026-09-22_solution_review_and_plan.md." `
  --allow-unlabeled-uid 1.2.826.0.1.3680043.8.498.73527530686853911124431549317032662220 `
  --output experiments/SPRINT943/validation_r2p_full.json
```

Для другой модели заменить `--predictions`, `--output` и **правдиво описать**
`--provenance`: источник весов, train/validation split и способ получения
прогнозов. `--prediction-kind` обязателен: `fold-out`, `in-sample` или `unknown`.
Название CSV и значение этого аргумента сами по себе не доказывают OOF.

Схема prediction CSV: `StudyInstanceUID,fold` и 12 target-колонок из таблицы выше.
Порядок строк и колонок не важен: join выполняется по UID. Дополнительные колонки
перечисляются в отчёте, но не участвуют в метрике. По умолчанию scores должны
быть конечными вероятностями [0,1]; для logits/ranks явно задать `--score-type`.
Другие label/fold-файлы можно передать через `--labels` и `--folds`.

Полное покрытие folds обязательно. Для заранее объявленного screen допустим
`--allow-partial`; отчёт будет отмечен как частичный. Отсутствующая label-строка
запрещена без явного `--allow-unlabeled-uid`. Частично пустые labels, NaN/Inf,
дубликаты UID/колонок, неизвестные UID и неверный fold завершают запуск с кодом 2.
Успешный запуск возвращает 0. Если у target остался один класс, его AUC и полный
macro равны JSON `null`, а не искусственному 0.5; отдельно дано среднее только
по определённым targets с указанием их количества.

## Ограничения и следующий эксперимент

1. Legacy: бинаризация мягкого score по `>=0.5`; UNK=0.28 попадает в negatives.
   Known-only: YES — positive, NO — negative, UNK исключается отдельно по target.
   Обе метрики используют weak labels, а не скрытую competition-разметку.
2. `FOLDS_V1` разделяет исследования. **Patient/site independence не доказана.**
   Перед выводами о переносимости проверить доступные patient/site группы.
3. В старых S22/S24 checkpoint выбирался по лучшей validation epoch этого же
   fold. Это источник оптимизма отбора. CSV guards не проверяют train history.
4. Не прогонять публичные competition checkpoints на train с последующим
   обозначением результата как OOF: для этого нужны модели, исключившие
   соответствующий fold при обучении, и подтверждённый train manifest.
5. Для развития публичной основы сначала воспроизвести один обучаемый компонент
   с сохранёнными split/checkpoint manifest и фиксированной процедурой выбора.
   Затем сравнивать новые варианты на тех же folds и обеих метриках. Подбор blend
   weights на тех же OOF labels создаёт оптимизм; для него нужен отдельный
   уровень validation. В этом evaluator подбор отсутствует.

## Проверка evaluator

Выполнены 1296 синтетических случаев rank-AUC против независимого попарного
определения (включая ties и отсутствие одного класса); проверены обычный
evaluation и семь отказов: duplicate UID, fold mismatch, NaN, probability >1,
неполное покрытие, неизвестный UID, неразрешённый отсутствующий label. Также
проверены явное разрешение unlabeled UID и отдельная маска UNK. Реальный CSV
R(2+1)D18 пересчитан без training/GPU и без изменения исходных данных.
